# 사건 개요(Story Digest) 프롬프트 평가

사건 페이지의 종합 개요는 `industry/prompts/story-digest.md`에 의해 생성됩니다. 이 프롬프트를 수정하기 전에, 동일한 사건 세트에 대해 기존 프롬프트와 후보 프롬프트를 나란히 실행하고 사람이 직접 품질을 비교·평가해야 합니다. 단순히 페이지에 노출된 느낌만으로 판단해서는 안 됩니다.

## 1. 평가 케이스 준비

```bash
node --env-file=.env scripts/eval-story-digests.ts --stories <사건id>,<사건id> --out .data/story-digest-cases.jsonl
```

사건 ID는 사건 페이지 URL인 `/story/<id>` 경로의 ID 부분입니다. 내보내기 작업은 데이터베이스만 읽으며, LLM을 호출하지 않고 어떤 사건 데이터도 변경하지 않습니다. 기사는 사이트에서 개요를 생성할 때와 동일한 규칙으로 조회되며, 단순 언급 기사, 종합 기사, 비공개 또는 철회된 기사는 제외됩니다. 이미 개요가 존재하는 사건은 "수정 후 재작성" 모드로 조립되며(이전 버전 개요 미포함), 개요가 없는 사건은 최초 작성 모드로 처리됩니다. 사건 ID를 찾을 수 없거나 이미 병합되었거나 사용 가능한 보도 기사가 없는 경우 에러가 발생합니다.

내보낸 파일은 라인당 1개 사건(JSONL)으로 구성되어 있어 미리 내용을 검토할 수 있습니다. 신규 기사가 추가되었을 때의 증분 업데이트(Incremental update)를 테스트하려면 `inputMode`를 `incremental`로 변경하고 `story.previousDigest` 및 `knownArticleIds`(이전 버전에 이미 포함된 기사 ID 목록)를 채워 넣으세요. 직접 케이스를 작성할 수도 있으며, 포맷은 `industry/story-digest-eval.example.jsonl` 예시를 참조하세요.

## 2. 병렬 비교 실행 (Side-by-side)

```bash
node --env-file=.env scripts/eval-story-digests.ts --cases .data/story-digest-cases.jsonl --system my-candidate.md
```

- 각 케이스별로 기존 프롬프트와 후보 프롬프트를 각각 1회씩 실행합니다. 동일한 모델(기본값은 현재 사이트의 "사건 개요" 단계에서 사용 중인 모델, `--models`로 변경 가능)과 동일한 입력을 사용합니다. 모델에 전송되는 시스템 프롬프트, 사용자 입력 및 샘플링 파라미터는 실제 사이트에서 개요를 생성할 때와 완전히 동일합니다.
- 후보 프롬프트 파일의 작성 방식은 `industry/prompts/`와 동일합니다. `{{siteName}}`은 사이트명으로 치환되며, `{{> 파일명}}`을 통해 공통 규칙을 임포트합니다. 누락된 변수가 있으면 오류가 발생합니다. 후보 프롬프트와 기존 프롬프트가 렌더링 후 완전히 동일한 경우 실행이 거부됩니다. `--system`을 지정하지 않으면 기존 프롬프트로만 실행됩니다.
- 실행 시작 전 총 호출 횟수(케이스 수 × 모델 수 × 프롬프트 수)가 출력되며, `--max-calls`(기본값 18)를 초과하면 단 한 건도 호출하지 않고 중단됩니다. 모든 호출은 실제 사이트의 타 모델 요청과 마찬가지로 감사 영수증에 기록되고 예산에 반영됩니다. 동일한 조건으로 재실행할 경우 이미 수신된 캐시 결과를 재사용하므로 추가 과금이 발생하지 않습니다. 따라서 후보 프롬프트를 수정하여 다시 실행해도 기존 프롬프트 쪽은 비용이 발생하지 않습니다.

평가 결과는 `.data/eval/`(`--out-dir`로 변경 가능)에 JSON 및 Markdown 형태로 각각 1부씩 저장됩니다. 양쪽의 제목과 개요가 나란히 비교 배치되며, 호출당 토큰 사용량과 레코드 번호, 실패한 호출의 사유가 명시됩니다.

## 3. 정성 평가 체크포인트 (사람이 확인할 사항)

신뢰할 만한 자동 채점 지표가 없으며, 본 도구는 LLM에게 LLM의 결과물을 채점하게 하지 않습니다. 사람이 다음 항목을 직접 확인해야 합니다:

- 하단의 타임라인을 날짜순으로 단순 나열하지 않고, 핵심적인 변화와 현재 시점의 결론을 두괄식으로 명확히 설명하고 있는가?
- 공허한 홍보성 문구나 판에 박힌 상투어가 포함되어 있지 않은가?
- 조건, 적용 대상, 요금 및 한도, 지역 제한 등의 제약 사항이 해당 객체에 올바르게 연결되어 있는가?
- 보도 및 팩트 근거에 없는 내용이 날조(환각)되거나, 보도 자체에 대한 메타 평가("보도에서 미공개...", "출처에 따르면...") 또는 프롬프트 작성 지침이 본문에 유출되지 않았는가?
- 수정 후 재작성 시, 이미 효력을 상실한 과거의 사실관계가 깨끗이 정리되었는가?

## 4. 프롬프트 수정 반영 후

프롬프트 버전을 교체하더라도 기존에 생성된 사건 개요가 즉시 일괄 재작성되지는 않습니다. 개별 사건은 해당 사건에 속한 보도 기사가 변경될 때만 다시 생성되며, 신규 보도가 들어올 때 기존 개요를 바탕으로 증분 업데이트되므로 대량의 모델 호출이 한꺼번에 발생하지 않습니다.

특정 몇몇 사건을 즉시 새 프롬프트로 강제 재작성하고 싶다면 프로젝트 루트에서 `rewriteStoryDigest` 스크립트를 호출하세요(사건당 1회의 모델 호출이 발생하며 백엔드 감사 로그에 기록됩니다):

```bash
node --env-file=.env --input-type=module -e '
const { rewriteStoryDigest } = await import("@aihot/backend/events/corrections");
const { sql } = await import("@aihot/backend/db");
const [s] = await sql`SELECT id FROM stories WHERE public_id = ${"<사건id>"}`;
if (!s) throw new Error("해당 사건 ID를 찾을 수 없습니다.");
console.log(await rewriteStoryDigest(s.id, "개요 프롬프트 업데이트에 따른 재작성", "ops-script"));
await sql.end();'
```
